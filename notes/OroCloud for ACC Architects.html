OroCloud for Adobe Commerce Cloud architects

Learn OroCloud by mapping it to what you already run on ACC. Each tab ends with key takeaways and a quick self-test.

Oro OroCloud / OroCommerceACC Adobe Commerce Cloudunconfirmed not verified in official docs

OroCloud is ACC Pro without git-push deploys.

Oro runs a single-tenant, Puppet-managed stack on Google Cloud or Oracle Cloud. You start every release yourself with orocloud-cli on a maintenance node you reach over VPN. Your customisation lives in one file, orocloud.yaml. Oro owns the topology: node counts, service versions and the queue layout change through support requests.

Five things that surprise ACC people

  • Backups cover the database, code and media, but not Elasticsearch or RabbitMQ. Plan a reindex after every restore.
  • Every upgrade removes patches applied with orocloud-cli patch:apply.
  • Zero downtime is a per-release choice. upgrade:rolling is only safe when the schema change is backward compatible, and that judgement is yours.
  • Only consumers that were running before an upgrade run after it. Check them after each deploy.
  • Oro's docs disagree on the cache command: cache:rebuild (7.0) vs app:cache:clear (7.1 dev). Run orocloud-cli list on your node.

Architecture overview

A CDN/WAF in front, at least two nginx + PHP-FPM web nodes, separate job nodes for consumers, a PostgreSQL failover pair, Elasticsearch, RabbitMQ, Redis with Sentinel, GridFS and an SMTP relay. Tap any box for its role, scaling model and failure impact.

Swipe sideways to see the whole diagram.

Request flow, step by step

  1. DNS points to Cloudflare or the Google LB, where TLS ends.
  2. GCP path: the Google LB forwards HTTP :80 and WebSocket :8080 to a web node. Cloudflare path: traffic arrives through the outbound cloudflared tunnel and nginx balances across web nodes. Web nodes have no public IPs.
  3. The nginx OroCloud WAF applies access_policy (IP, ASN, country, user agent, URI; blocked requests get 451), bot testcookie and Naxsi checks, then rate limits (429/503).
  4. PHP-FPM boots Symfony and reads the session and caches from Redis. Default DSNs: session /0, cache /1, Doctrine /2, layout /3.
  5. The app reads and writes PostgreSQL. Storefront search and listings query the Elasticsearch website index. Media comes from GridFS.
  6. Heavy work (reindex, price recalculation, imports, emails) is published to RabbitMQ and the response returns immediately.
  7. Consumers on job nodes process the messages. Cron (oro:cron) triggers scheduled commands, many of which also run as messages.
  8. Mail leaves through the SMTP relay. Outbound API calls leave through the NAT node's fixed IP, which is the address partners allow-list.

Key takeaways

  • Same shape as ACC Pro: edge, HA web tier, async workers, managed data services.
  • Consumers are long-running daemons on dedicated job nodes, not cron-spawned.
  • Two search indexes: back office (oro_search) and storefront (oro_website_search).
  • With Cloudflare there is no public origin IP. The web tier is reachable only through the tunnel.
  • Elasticsearch and RabbitMQ are outside backups.

Key takeaways

  • .magento.app.yaml hooks become command lists in orocloud.yaml.
  • env.php becomes ORO_* env vars and .env-app* files.

OroCloud on OCI vs GCP

For application and deployment work the two behave the same. Oro documents only two practical differences: the edge (Google CDN is GCP-only) and self-service logs (documented for the GCP console only).

How to tell which cloud an environment runs on

  1. Ask Oro Support or check your onboarding pack. Oro sends primary and DR IP addresses at onboarding. Whether it names the provider is unconfirmed.
  2. You were given GCP console / Logs Explorer access → GCP. Strong indicator, by inference.
  3. Response headers. server: cloudflare or cf-ray means Cloudflare (either cloud). via: 1.1 google means the Google LB, so GCP. unconfirmed heuristic
  4. ASN of the NAT egress IP (Google vs Oracle). unconfirmed heuristic
  5. From an SSH session: /sys/class/dmi/id/sys_vendor, or the provider metadata endpoints. May be blocked. unconfirmed
# edge: cloudflare vs google LB
curl -sI https://your-store.example.com | grep -iE '^(server|via|cf-ray):'

# on the node (may be blocked)
cat /sys/class/dmi/id/sys_vendor

Hostnames such as ocom-<project>-prod1-maint1 do not encode the provider.

Key takeaways

  • OCI means Cloudflare at the edge, with no public origin IP.
  • On OCI, ask support how you get application logs. Only GCP tooling is documented.
  • Deploy commands, backups and topology are the same on both.
  • There is no official CLI flag that shows the IaaS.

Deployment strategy

On OroCloud you run every release from the maintenance node. orocloud-cli clones a tag, branch or commit from your repo, and only one operation runs at a time. deploy is the first install only; every later release is an upgrade* or app:package:* command.

Three upgrade modes

upgradedowntime
  1. Maintenance on, stop consumers, cron, websocket
  2. Checkout + composer install
  3. oro:platform:update incl. assets
  4. Warm layout caches
  5. Maintenance off

Use for any change, including destructive migrations and LTS upgrades.

upgrade:rollingno downtime
  1. Checkout + composer
  2. Build assets
  3. oro:platform:update --skip-assets
  4. Warm caches
  5. Restart services

Use for backward-compatible schema changes: no dropped or altered columns.

upgrade:sourceno downtime
  1. Checkout + composer
  2. Build assets
  3. Warm caches
  4. Restart services

Use for code-only changes. Skips oro:platform:update, so no new entities or fields.

All modes skip reindexing by default. Add --schedule-search-reindexation when needed; Oro requires a reindex for LTS-to-LTS upgrades.

  3. Deploy hook: maintenance on, setup:upgrade, SCD if on deploy

Rollback

Where it failedDo this
Before oro:platform:updateorocloud-cli maintenance:off. The database is untouched.
During or after migrationsorocloud-cli backup:restore <date> restores DB and code and rebuilds caches. Then reindex. Media restores need support.
Code-only bug, no migrations ranRedeploy the previous package with app:package:deploy --source. No instant blue/green rollback is documented unconfirmed.

maintenance:on stops the web server and consumers, cron and websocket. emergency:on puts only the web server in maintenance and keeps services running.

Release runbook

# 0. validate config
orocloud-cli config:validate

# 1. stage: build once, deploy, test
orocloud-cli app:package:build <tag> --label="R-2026.11"
orocloud-cli app:package:list
orocloud-cli app:package:deploy --rolling <package>   # or no flag if destructive

# 2. prod: back up, then promote the same package
orocloud-cli backup:create --label=pre-R-2026.11
orocloud-cli app:package:deploy --rolling <package>

# 3. verify
orocloud-cli log:list
orocloud-cli log:view <file>
orocloud-cli app:console "oro:website-search:reindex --scheduled"   # if needed

Key takeaways

  • Choose downtime per release: upgrade, upgrade:rolling or upgrade:source.
  • App packages cut maintenance from 800 s to 230 s in Oro's test.
  • Always backup:create before prod; rollback is backup:restore plus a reindex.
  • Upgrades remove patch:apply patches. Commit real fixes to the repo.
  • After a deploy, confirm consumers and cron are running.

Command cheat sheet

App commands run as php bin/console <cmd> --env=prod locally, or as orocloud-cli app:console "<cmd>" on OroCloud (1-hour timeout, 2 GB memory; quote anything with arguments).

Key takeaways

  • Wrap any app command in orocloud-cli app:console "…" on OroCloud.
  • Storefront search is oro:website-search:reindex; use --scheduled in prod.
  • The cron entry point is oro:cron, not oro:cron:run.
  • Raw prod dumps can't be downloaded; use sanitized backups.
  • Not sure of a name? orocloud-cli list and --help are the source of truth.
